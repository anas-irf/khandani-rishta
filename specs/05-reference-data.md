This document holds the seed content of every lookup table and every closed option list. The codes here are the values stored in the database and sent over the API. Labels are English only at launch; `name_ur` and `label_ur` stay `NULL` until the Urdu phase.

## 1. Storage, seeding and serving

### 1.1 Two kinds of reference data

| Kind | Examples | Stored in | Changed by |
|---|---|---|---|
| Closed option lists | `marital_status`, `employment_type`, `photo_visibility` | The API source code and the schema `CHECK` constraints | A code change plus a migration |
| Lookup tables | `religions`, `sects`, `castes`, `languages`, `education_levels`, `education_fields`, `profession_categories`, `income_bands`, `hobbies`, `countries`, `regions`, `cities` | PostgreSQL (04 section 3) | A migration, or the admin console for castes (18 section 6) |

Closed option lists are closed because code branches on their values. Their labels live in one Rust module, `apps/api/src/reference/options.rs`, as a static table of `(list, code, label, label_ur)` in display order. Section 2 is the content of that module. A unit test must insert every code of every list into a throwaway database row to prove the module and the `CHECK` constraints agree.

### 1.2 Codes

1. A code is lowercase ASCII letters, digits and underscores, and starts with a letter: `^[a-z][a-z0-9_]*$`.
2. A code never changes after release. To rename something, change the `name`. To retire it, set `is_active = false`.
3. A sub-caste code is `<parent code>_<clan slug>`, for example `rajput_bhatti`. The slug is the name in lowercase with spaces replaced by underscores and every other non-alphanumeric character removed. A few codes do not follow this pattern because the usual name puts the clan first (for example `memon_sindhi` for "Sindhi Memon"): the tables in section 5.3 are the authority, not the rule.
4. Income band codes are `<currency in lowercase>_<rank>`, for example `pkr_3`.

### 1.3 Seeding

| Migration | Seeds |
|---|---|
| `0011_seed_reference_data.sql` | Sections 3 to 11 of this document, written by hand as `INSERT` statements |
| `0012_seed_geography.sql` | Countries, regions and cities, generated by a script (section 12) |

`sort_order` for hand-written rows is the row's position in its table below multiplied by 10 (10, 20, 30 and so on), so later rows can be inserted between existing ones. Rows named "Other" always get `sort_order = 9990` so they stay last.

### 1.4 Caching and serving

1. At startup the API loads all lookup tables except `regions` and `cities` into memory (a struct behind `Arc`, replaced as a whole on reload).
2. The cache is reloaded every 10 minutes and immediately after any admin change to castes.
3. `GET /v1/reference/bootstrap` serves the cache plus the option lists. `version` is the first 16 hexadecimal characters of the SHA-256 of the serialised body, and is also the `ETag`.
4. Only rows with `is_active = true` are served. Validation of incoming codes accepts active rows only. A profile that already holds a retired code keeps it, and the API still resolves its name for display.
5. Clients store the bootstrap body on disk, revalidate it with `If-None-Match` at start, and resolve every code to its label locally. An unknown code is shown as the code with underscores replaced by spaces.

Sensitivity note, flagged for the product owner: the Ahmadi community is not listed as a sect of Islam. Pakistani law (Penal Code sections 298-B and 298-C) forbids presenting it that way, and listing it would put both those members and the operator at risk. Such members choose the religion `other`. The product owner should confirm this choice before launch.

## 5. Castes and sub-castes

### 5.1 How to read this seed

1. The caste (zaat, biradari) is optional on every profile. The picker has two entries that are not rows: "Other", which opens a free-text field saved to `caste_other` or `sub_caste_other`, and "Prefer not to say", which saves `NULL`.
2. `castes` has two levels. Section 5.2 lists the top level (`parent_code` is `NULL`). Section 5.3 lists sub-castes by parent.
3. Clan membership is contested. The same clan name is claimed by several castes (Bhatti, Khokhar, Sial, Kharal, Wattoo and Chauhan are claimed by both Jutt and Rajput families). In this seed a sub-caste row belongs to exactly one parent, and the same clan name can appear under more than one parent with different codes (`rajput_bhatti` and `jutt_bhatti`). Members pick the one their family uses, or type their own.
4. Many people identify by a clan or title alone (Bhatti, Butt, Malik, Chaudhry, Mirza). Those names also exist as top-level entries so nobody is forced to choose a parent group they do not use.
5. A partner preference lists top-level codes only (04 section 5.6). A member who picked the top-level entry `bhatti` does not match a preference for `rajput`. The picker therefore shows the broad group first and offers the standalone clan entries after it.
6. `aliases` hold other spellings. The picker's search matches the name and every alias.
7. The parent assignments below are editorial and come from general knowledge, public matrimonial sites and encyclopaedia lists. They must be reviewed by people from the communities concerned before launch. Wrong assignments are corrected with a migration that adds rows; codes already released are never renamed (section 13).
8. This list offers no ranking of castes. Rows are sorted alphabetically by name in pickers, with the 12 most common entries (the first 12 rows of 5.2) pinned to the top.

## 7. Education levels

`rank` drives "at least" preferences (`partner_preferences.education_min_rank`): a candidate satisfies the preference when their level's rank is greater than or equal to the minimum.

| code | name | rank |
|---|---|---|
| `below_matric` | Below Matric | 1 |
| `matric` | Matric or O-Level | 2 |
| `intermediate` | Intermediate or A-Level (FA, FSc, ICS, ICom) | 3 |
| `diploma` | Diploma (DAE or similar) | 4 |
| `bachelors` | Bachelor's (BA, BSc, BS, BE, BBA) | 5 |
| `dars_e_nizami` | Dars-e-Nizami | 5 |
| `professional` | Professional degree (MBBS, BDS, Pharm-D, LLB, CA, ACCA) | 6 |
| `masters` | Master's (MA, MSc, MBA) | 6 |
| `mphil` | MPhil or MS | 7 |
| `doctorate` | Doctorate (PhD) | 8 |

Ties are deliberate:

1. `professional` and `masters` share rank 6. A preference of "master's or higher" therefore accepts a doctor, a lawyer or a chartered accountant.
2. `bachelors` and `dars_e_nizami` share rank 5. Religious education is placed level with a bachelor's degree for matching. This is a simplification, not a statement about formal equivalence.
3. Two levels with the same rank are equal for every comparison. `sort_order` alone decides their order in pickers (the order of the table).

The preference picker for minimum education shows one entry per distinct rank, labelled with the first level of that rank ("Bachelor's or higher", "Master's or professional degree or higher").

## 10. Income bands

Monthly income. `profiles.income_band_code` is optional; "Prefer not to say" saves `NULL`.

### 10.1 Rank equivalence

Every currency has seven bands with ranks 1 to 7. The same rank in two currencies means roughly the same standing within that country, not the same amount after conversion. A member abroad who earns an average professional salary and a member in Pakistan who earns an average professional salary land on the same rank. `partner_preferences.income_min_rank` compares ranks only, so a preference works across currencies with no exchange rates.

The overseas amounts below are editorial starting values. The product owner may adjust the amounts in a migration at any time; the ranks and codes stay.

### 12.2 Input files

| File | Used for | Format |
|---|---|---|
| `countryInfo.txt` | `countries` | Tab-separated, comment lines start with `#`. Columns used: 1 `ISO` (alpha-2), 5 `Country` (name), 13 `Phone`. |
| `admin1CodesASCII.txt` | `regions` | Tab-separated: `code` (for example `PK.04`), `name`, `asciiname`, `geonameid`. |
| `PK.zip` (contains `PK.txt`) | Pakistani cities | The standard GeoNames table, tab-separated, 19 columns. |
| `cities15000.zip` (contains `cities15000.txt`) | Cities in the rest of the world | Same 19 columns. |

Columns of the GeoNames table used by the script (1-based): 1 `geonameid`, 3 `asciiname`, 5 `latitude`, 6 `longitude`, 7 `feature class`, 8 `feature code`, 9 `country code`, 11 `admin1 code`, 15 `population`.

### 12.3 The generator script

`scripts/build-geo-seed.mjs`, a plain Node.js script with no dependencies beyond the Node standard library plus one unzip helper. It is run by hand when the geography needs refreshing, never in CI and never at runtime. The generated SQL file is committed.

```text
node scripts/build-geo-seed.mjs
  1. Download the four input files into scripts/.geo-cache/ (git-ignored). Reuse cached files younger than 7 days.
  2. Build countries, regions and cities in memory with the rules below.
  3. Write apps/api/migrations/0012_seed_geography.sql.
  4. Print the three row counts.
```

Rules for `countries`:

1. One row per line of `countryInfo.txt` that has a two-letter `ISO` code.
2. `code` = `ISO`. `name` = `Country`. `name_ur` = `NULL`. `is_active` = `true`.
3. `dial_code`: take the `Phone` column, keep the part before the first space, remove hyphens, and prefix `+`. Empty stays `NULL`. Example: `92` becomes `+92`; `1-809 and 1-829` becomes `+1809`.
4. `sort_order`: Pakistan 10, Saudi Arabia 20, United Arab Emirates 30, United Kingdom 40, United States 50, Canada 60, Australia 70, Qatar 80, Kuwait 90, Oman 100, Bahrain 110, Germany 120, Italy 130, Malaysia 140. Every other country gets 1000. Pickers order by `sort_order`, then `name`.

Rules for `regions`:

1. One row per line of `admin1CodesASCII.txt` whose country exists in `countries`.
2. `id` = the line's `geonameid` (stable across regenerations). `country_code` = the part of `code` before the dot. `name` = `asciiname`.
3. Keep a map from the full `code` (for example `PK.04`) to `id` for the city step.
4. When two regions of one country have the same `asciiname`, append the admin code in parentheses to the second one so the `UNIQUE (country_code, name)` constraint holds.

Rules for `cities`:

1. Candidates: every line of `PK.txt`, plus every line of `cities15000.txt` whose country code is not `PK`.
2. Keep a line only when `feature class` is `P` and `feature code` is one of `PPL`, `PPLA`, `PPLA2`, `PPLA3`, `PPLA4`, `PPLC`, `PPLG`, `PPLL`, `PPLS`. This drops sections of cities (`PPLX`), abandoned and historical places.
3. For Pakistan keep only lines with `population >= 1000`. The other file is already limited to a population of 15,000 or more.
4. `id` = `geonameid`. `name` = `asciiname` (plain ASCII, so members can type it on any keyboard). `country_code`, `latitude`, `longitude`, `population` from the line. `region_id` = the map lookup of `<country code>.<admin1 code>`, or `NULL` when missing.
5. `is_major` = `population >= 100000` for Pakistan, `population >= 500000` elsewhere.
6. Deduplicate on `(country_code, region_id, name)`, keeping the line with the larger population.

Rules for the output file:

1. Header comment with the generation date, the GeoNames attribution text and the three row counts.
2. `INSERT` statements in batches of 500 rows, in the order countries, regions, cities, each ending with `ON CONFLICT DO NOTHING`.
3. Strings are escaped by doubling single quotes.
4. After the inserts, move the identity sequences past the explicit ids:

```sql
SELECT setval(pg_get_serial_sequence('regions', 'id'), (SELECT max(id) FROM regions));
SELECT setval(pg_get_serial_sequence('cities', 'id'), (SELECT max(id) FROM cities));
```

### 12.4 Expected size

| Table | Expected rows | Note |
|---|---|---|
| `countries` | About 250 | |
| `regions` | About 3,900 | Pakistan has seven or eight rows depending on the GeoNames release |
| `cities` | About 25,000 from `cities15000` plus the Pakistani places of 1,000 or more people | The Pakistani count is not known in advance |

These are estimates. The script prints the real numbers; record them in the header comment of the generated file. If the generated file exceeds 8 MB, raise the Pakistani population threshold to 2,000 and regenerate.

### 12.5 Places missing from the seed

A member whose city is not found types it into `city_other` (or `origin_other` for the family's home town). Moderators do not review these. If the same missing place is typed often, add it by hand in a later migration with an id of 900,000,000 or above so it can never collide with a GeoNames id.

## 13. Maintenance rules

| Task | How |
|---|---|
| Add a row to any lookup table | A new migration with an `INSERT`. Choose a `sort_order` between its neighbours. Never reuse a retired code. |
| Rename a row | A migration that updates `name`. The code stays. |
| Retire a row | A migration (or the admin console for castes) that sets `is_active = false`. Never `DELETE`: profiles may reference it. |
| Add a value to a closed option list | Three changes in one pull request: a migration that replaces the `CHECK` constraint, the new row in `options.rs`, and the Rust enum variant. Then export the OpenAPI document again. |
| Remove a value from a closed option list | Not allowed once released. Hide it in the clients instead. |
| Promote a caste suggestion | Admin console, `POST /v1/admin/caste-suggestions/{id}/promote` (18 section 6). The API inserts the `castes` row, sets the suggestion to `promoted` with `promoted_code`, and updates every profile whose `caste_other` (or `sub_caste_other` under the same parent) normalises to the suggestion's `normalized_name`: it sets the code column and clears the free-text column. |
| Reject a caste suggestion | Sets the suggestion to `rejected`. Profiles keep their typed value. A rejected name is not suggested again: later uses only increase `usage_count`. |
| Record a typed caste | When a profile is saved with `caste_other` or `sub_caste_other`, the API upserts `caste_suggestions` on `(COALESCE(parent_code, ''), normalized_name)`, increasing `usage_count`. `normalized_name` is the trimmed value in lowercase with runs of whitespace collapsed to one space. A typed value that equals the name or an alias of an existing active row (after the same normalisation) is replaced by that row's code and no suggestion is recorded. |
| Refresh geography | Run `node scripts/build-geo-seed.mjs`, review the diff, and commit the output as a new migration file with the next number (never edit `0012`). The new file uses `ON CONFLICT (id) DO UPDATE` for names and population. |
| Add Urdu labels | A migration that fills `name_ur` and `label_ur`, plus the `label_ur` column of `options.rs`. Nothing else changes. |
