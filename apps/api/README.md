# Khandani Rishta API

The Rust (Axum) API behind the web and Android apps. It implements `specs/` literally: the schema of `specs/04-database-schema.md`, the states and limits of `specs/03-domain-model.md` and the endpoints of `specs/15-api-contract.md`. One binary runs the HTTP and WebSocket server, two background job workers and the scheduler (`specs/19-jobs-and-realtime.md`).

## Running

| Task | Command (in `apps/api`, database running) |
|---|---|
| Start the database | `docker compose -f ../../infra/local/docker-compose.yml up -d` (host port 5433) |
| Run the API | `cargo run` (listens on `BIND_ADDR`, 127.0.0.1:8787 locally; applies migrations first) |
| Fake members for local use | `cargo run -- seed-dev` (600 profiles; refuses `APP_ENV=production`) |
| Export the contract | `cargo run -- openapi > ../../packages/api-contract/openapi.json`, then `pnpm generate:api-client` at the root |
| Checks | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` |

Configuration comes from `.env` (copy `.env.example`). Only `DATABASE_URL` is needed locally: every integration whose variables are empty is switched off rather than failing (R2 uploads answer 503, moderation falls back to the manual queues, email and push are skipped). Use `127.0.0.1` rather than `localhost` in `DATABASE_URL` on Windows; `localhost` adds about two seconds to every new connection. Real sign-in needs the Clerk variables of `specs/06-auth-and-accounts.md` section 13.

## Layout

| Path | What lives there |
|---|---|
| `src/routes/` | HTTP handlers, one file per row of 15 section 17, thin: extract, call `db`/`domain`/`views`, map to a model. Staff routes are in `routes/admin/`. |
| `src/views/` | The only place other members' profiles are assembled: `ProfileCard`, `ProfileDetail`, `Relation`, `PhotoView` under the privacy rules of 09 (S-05). |
| `src/domain/` | Pure rules with unit tests and no I/O: gate, visibility, display, matching, completeness, preference defaults, text rules, chat safety, identity numbers. Enums of every closed list are in `options.rs` (generated from 05 section 2) and `types.rs`. |
| `src/db/` | SQL, one file per aggregate. Runtime `sqlx` queries with bound parameters (no compile-time macros, so no offline query data is needed). |
| `src/models/` | Request and response types (`serde`, `utoipa::ToSchema`). |
| `src/auth/` | Clerk token verification, the cached account snapshot, first-request provisioning and the access-level extractors (`Auth`, `Open`, `Connected`, `Engage`, `Browse`, `Moderator`, `Admin`). |
| `src/jobs/` | The job queue in PostgreSQL: worker, scheduler and one file per job kind of 19 section 2. |
| `src/realtime/` | The in-process WebSocket hub and the session loop of `GET /v1/ws`. |
| `src/services/` | Outbound integrations behind traits: Clerk, R2, Azure Content Safety, Resend, FCM, and the identity number encryption. |
| `src/notify.rs`, `src/notify/` | The `notify` helper and the notification catalogue of 14 section 2 (feed row, push and email per event). |
| `src/lifecycle.rs`, `src/sanctions.rs`, `src/audit.rs` | Shared state transitions: ending connections, suspensions and bans, the staff audit log. |
| `src/settings.rs`, `src/reference/` | `app_settings` with coded defaults (60-second cache) and the reference data cache with the bootstrap body. |
| `migrations/` | `0001` to `0010` from 04, the reference and geography seeds (`0011`, `0012`, the latter generated by `scripts/build-geo-seed.mjs`) and the settings seed (`0013`). Append-only. |

## Tests

`cargo test` runs the unit tests and the `#[sqlx::test]` tests, each of which gets a fresh database with every migration applied. `src/test_support.rs` builds the app around fakes of every integration (`TestApp`), mints Clerk-style tokens with a fixed test key, and has fixtures for members in any state (`member`, `member_of`, `member_with`, `draft_user`, `staff`). WebSocket tests serve the app on a local port (`TestApp::serve`).
